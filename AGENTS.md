# marfa-swift

The Swift SDK for Marfa, as the Swift package `Marfa`: Swift types, `async` calls, change streams and errors over `MarfaCore`, the Rust engine from `withmarfa/marfa` that every native client embeds. The core does the networking, storage and syncing.

## Layout and build

- `MarfaCoreFFI` is the core as a binary, `Frameworks/MarfaCoreFFI.xcframework`, gitignored; a release tag points it at a prebuilt archive instead. `MarfaCore` is its UniFFI glue, `Sources/MarfaTypes` the server's wire types and `Sources/MarfaAPI/Generated` the client for the server's own operations, all generated, committed and never edited. `Marfa` is the hand-written layer apps import. `MarfaAPI` calls the server directly for what only the server can do, such as registering a type; `generator/generate.mjs` chooses its operations by a rule, and `generator/generate.test.mjs` pins the rule on a fixture and checks named operations in the committed client, so a pin that adds an operation regenerates the client and needs no change there.
- `MarfaTesting` provides `WorkingCopy.fake(...)` for app tests and previews. Its `FakeCopy` wraps a `WorkingCopy` over `InMemoryCore`, a pure-Swift `CoreProtocol` with no Rust, store, or server. `CoreHolder` holds any `CoreProtocol`, so the copy's code is unchanged. Its sources are wrapped in `#if DEBUG`, so a release build holds none of it. It is not a second engine: a call, or an input to a supported call, that it cannot match exactly and cheaply throws `FakeCopyError.unsupported`; new core calls fail compilation until the fake implements them. Offline public API tests for supported calls belong in `Tests/MarfaBehaviorTests`, using `@Test(arguments: CopyKind.allCases)`, and must pass on both copies. If the fake cannot match, narrow its supported calls rather than weaken the test. Tests requiring a reopened store, a damaged file, hydration, or a server stay in `MarfaTests`. Its `FakeCore` scripts the Rust core's watch, gates, and drop, outside `InMemoryCore`'s scope.
- `MarfaIcons` draws an item type's icon, an Iconify ID `<set>:<name>` from the closed list of sets marfa pins: `lucide:` and `simple-icons:`. `ItemType.icon` and `TypeIcon(id:)` take the full ID, and a bare name, an unknown set or an unknown name draws the fallback. `LucideSymbols.swift` is the hand-checked table from a `lucide:` ID to an SF Symbol. `MarfaBrandIcons` is a separate product holding the `simple-icons:` artwork, so an app that leaves it out ships none; `MarfaBrandIcons.register()` hands it to `MarfaIcons` (`BrandArtwork`), which never depends on it, and without that call a brand ID draws the fallback. `scripts/icons.mjs` reads marfa's `icon-set-lucide.json` and `icon-set-simple-icons.json` from the checkout `scripts/core.sh` used, and regenerates `LucideIconSet.swift` and `Lucide.xcassets` (the SVG of every pinned ID the table leaves out) in `MarfaIcons`, and `SimpleIconsIconSet.swift` and `SimpleIcons.xcassets` (every brand mark) in `MarfaBrandIcons`, with the artwork taken from the `@iconify-json/lucide` and `@iconify-json/simple-icons` releases the lists name. A pin bump that changes either release or list needs `scripts/icons.mjs` run in the same change, and `Tests/MarfaIconTests` and `Tests/MarfaBrandIconTests` fail until it is; with `MARFA_MONOREPO` set they also compare the generated lists to the checkout's.
- `MarfaTelemetry` is the optional reporter: errors as PostHog `$exception` events and logs as OTLP/HTTP JSON, with no third-party dependency, no token and no default destination, inert until an app configures it (`Telemetry.shared.configure(_:)`) and turns `isEnabled` on. Nothing reaches a body but a `StaticString`, a number, a boolean, the app's own configuration, the operating system and chip, a count of withheld exceptions, or a server refusal code that `FixedErrorText.isCode` accepts: `MarfaError.fixedText` in `Marfa` is the exhaustive `switch` that gives an error's fixed type and sentence, so a new `MarfaError` case needs both written before it compiles, and neither may include a value the error carries. `ExceptionLimiter` allows one exception for each type and operation in 60 seconds and 30 an hour, and the tests inject the transport and the clock and use no network beyond a loopback server. It has its own `PrivacyInfo.xcprivacy`.
- `core.pin` names the commit of a marfa release the package is built against, never a commit between releases. It stays a commit SHA, since `scripts/core.sh`, `ci.yml` and `release.yml` read it as one. `scripts/core.sh` builds the core at that commit, copies the framework and glue in, and regenerates the wire types and the client; it needs the Rust toolchain. By default it fetches the pinned commit into `.build/marfa`, a build input like any other under `.build/`, never a working clone: do not edit, branch or commit there. With `MARFA_MONOREPO` it builds from a clean checkout already at the pin instead, such as a detached worktree of an existing marfa clone. CI fails when the committed glue, wire types or client differ from what the pin generates.
- Then `swift build` and `swift test`. Live tests run against the server that `MARFA_API_URL` and `MARFA_API_KEY` name and are skipped by name without them; `MARFA_LIVE_REQUIRED` makes a missing server fail. marfa's `core/scripts/server-up.sh` boots one from the pinned checkout once `pnpm install --frozen-lockfile` and `pnpm --filter "@withmarfa/server..." build` have run there; export its `MARFA_TEST_URL` and `MARFA_TEST_KEY` as `MARFA_API_URL` and `MARFA_API_KEY`, and stop it with `core/scripts/server-down.sh`.
- The folder tests list every folder they add in a registry under the temporary directory, which they name in `MARFA_FOLDER_REGISTRY` before any folder call reads it, never the Mac's own. `MARFA_CLI` names a `marfa` binary built at the pin, for the test that holds the package's registry to the one `marfa folders list` reads; it is skipped by name without one, and `MARFA_LIVE_REQUIRED` makes a missing one fail. Folders are macOS only.
- No test reads or writes an item in the login keychain or raises a dialog. A test that keeps a key uses `inIsolatedKeychain`, in the test target only: a keychain file outside the search list with prompts refused for the process. CI compares the login keychain's generic passwords under the tests' service before and after the suite; it checks nothing else, and nothing checks a local `swift test`.
- `Examples/MarfaSample` is the sample app. `xcodegen generate` makes its project, which is gitignored.
- `.github/workflows/ci.yml`'s `Build + test` is the full build and test: every format rule, the core at the pin, every generated source, the command line at the pin, a `swift build` with no warning outside the generated wire types and client, the live tests against a booted server, both sample builds, and the sample's scenario offline and back. A test that fails is run once more (`swift test --repeat-until pass --maximum-repetitions 2`), and `scripts/test-verdict.sh` decides the result from the event stream, since `swift test` exits 1 even when the second try passed: a test whose last try passed does not fail the run, and the job summary and a warning name it as flaky, so fix it; one whose last try failed fails the run. Swift Testing is the only test framework, so the stream covers every test. A failed run keeps its build and test logs for three days.
- `scripts/lint.sh` is the format lint. Run it before a push. `ci.yml`'s `Lint Swift` runs `scripts/lint.sh --portable` on Linux, in the Swift release's container, so a format mistake fails a pull request in seconds without a Mac, and `Build + test` does not start until it passes. `--portable` leaves out `BeginDocumentationCommentWithOneLineSummary`, which splits a comment into sentences differently on Linux; `Build + test` runs every rule.
- `ci.yml`'s `Lint workflows` runs actionlint on every workflow and shellcheck on `scripts/` for every pull request and push, whatever it changes.
- A draft pull request runs only the quick checks on Linux: `Lint workflows` and `Lint Swift`. It starts no `Build + test`, and so no Mac. The last job, `Full CI`, waits for every other job and fails if any failed or was cancelled; a skipped job counts as passed. On a draft it is named `Draft CI`, so the required `Full CI` stays expected, and blocks a merge, until the run that marking the pull request ready starts has finished. Without that, skipped jobs would let a pull request merge in the moment between marking it ready and the first full run. Marking it ready for review, and every push after, runs everything. `Full CI` and `Pull request description` are the required checks, since a merge waits only on required checks.
- `scripts/ci-changes.sh` decides whether a pull request, or a push to `main`, runs `Build + test`: Markdown anywhere, `LICENSE`, `.claude/`, `.codex/`, `.githooks/` and `.github/` other than `workflows/` do not, and an unnamed path, a fixture, a workflow, `core.pin` and an empty or unreadable diff do. A draft is classified like any other pull request, and when the answer is true its `Build + test` still does not start. A push is classified only when the commit before it has a green `ci.yml` push run, and runs in full otherwise, so a documentation commit never shows green over one that was red or unchecked. A skipped job passes its required check; `scripts/ci-changes.test.sh` pins the rules and runs first in the job. The core is rebuilt only when `core.pin`, `scripts/core.sh` or `generator/` changes and no cache holds the result; otherwise the job reuses what that pin generated.
- The Actions cache holds only small entries, so none is evicted before it is used: `core-output` (the framework and everything generated, about 50 MB), `marfa-cli` (the command line, 14 MB), `cargo-swift`, the generator's build and pnpm's. No cargo build folder is cached: the two of them were 3.6 GB, and they evicted the entries a run needs. A miss still builds the core, from nothing. Only a run on `main` saves them, which every pull request can read: the push to `main` after a pin bump merges runs `ci.yml`, which builds the core and the command line for the new pin and saves both, so the first pull request after that builds no Rust. The pin bump itself saves nothing, because it checks out code this repository does not control.
- `.github/workflows/pin-bump.yml` runs from `main` only: daily as a backstop, by hand as a dry run (it builds and pushes nothing) unless `dry_run` is turned off, and from marfa's release agent with `dry_run` off when Marfa publishes a release. It resolves the newest published release of withmarfa/marfa (not a draft, not a prerelease) and the commit its tag points at, peeling an annotated tag; a published release has already passed marfa's release workflow, so it checks nothing else about marfa. When that commit differs from `core.pin` and no open pull request changes `core.pin`, it moves the pin on the branch `automation/core-pin`, regenerates the glue, wire types and client, builds, and hands the change to a second job as a patch, because the build runs code this repository does not control and holds no secret. The second job refuses a patch that touches anything but the pin and the generated sources, applies it, and opens a pull request titled `chore(package): move to marfa <tag>` as the WithMarfa Bot app with an auto-merge armed (the checks on a pull request that the GitHub token opens wait for someone to approve them, so it uses the app's token, limited to contents and pull requests). `.github/workflows/pin-bump-release.yml` runs the release whenever a pull request from that branch merges, so a bump fixed by hand is released too; a pull request from another branch that moves the pin starts no release. A bump that cannot build, because the package no longer compiles against the new core, opens no pull request. It opens an issue titled `Nightly failed: Bump the core pin`, the title withmarfa/marfa's scheduled workflows use, and each later failure comments on it (`scripts/report-pin-bump-failure.sh`). A bump whose checks fail stays open and stops the next one: the session that finds it fixes it or closes it, and one that moves the pin by hand first looks for an open pull request that changes `core.pin`. `scripts/pin-bump.sh` holds the decision and `scripts/pin-bump.test.sh` pins it.
- `.github/workflows/codeql.yml` analyzes Actions, and `codeql-swift.yml` analyzes Swift. `codeql.yml` runs once a week, on every pull request that is not a draft and on every push to `main`, and skips a change that is only Markdown, the license, `.claude/`, `.codex/`, `.githooks/` or `.github/ISSUE_TEMPLATE/`. `codeql-swift.yml` runs on macOS, where the organization has five runners, so it runs once a week (Monday, after the daily pin bump) and by hand, never on a pull request or a push: there it ran beside `ci.yml` and built the same core twice. Neither is a required check. The Swift job builds the library targets for one architecture beside the framework `ci.yml` caches for the pin, so a change to that cache's paths or key changes both workflows. `codeql.yml`'s concurrency group separates a draft pull request from a ready one, so marking a draft ready never cancels the full run, and gives a push to `main` its own group, so a later push never cancels it.

## Versions

- A version is a tag on this repository, which is where SwiftPM reads versions from, created when a logical set of merged work is ready, by the session that finishes that set unless its brief says not to, each the previous plus 0.0.1 whatever the change, as `v0.0.1`, `v0.0.2` and so on. No one writes a version into a file.
- `.github/workflows/release.yml`, run from `main`, makes a release. With `dry_run`, the default, it builds the core at the pin and an app on the archived framework without Rust. Without it, it also tags the next version on a commit on top of `main` that only points the binary target at the release's archive and checksum, publishes the release from the `release` environment, which only `main` can deploy to, and builds an app on it by URL.

## Writing

- Public prose (README, docs, issues, pull requests) follows the Google developer documentation style guide, in American English, with docs organized by Diátaxis: tutorials, how-to guides, reference and explanation kept apart.
- Code comments follow the language's own conventions. A comment stays only if it says what the code cannot: a constraint from outside, a non-obvious reason, a trap. Never what the code does, history, a ticket or a person. When in doubt, it goes.
- Words people read in an app follow the Writing section of Apple's Human Interface Guidelines, with the Apple Style Guide for terms.

## Working here

- American English in code, comments and commits. Scoped Conventional Commits (`feat(package):`, `fix(ci):`).
- Make worktrees in `.claude/worktrees/` (`git worktree add .claude/worktrees/<name> -b <branch> origin/main`). Once the work is merged, remove the worktree and its local branch (`git worktree remove`, then `git branch -D`, because git sees a squash-merged branch as unmerged) and run `git pull --ff-only` on `main`. If git refuses a removal, report it rather than forcing it.
- Feature branches and pull requests; never push `main`. A session merges its own pull request once every required check is green and the review its risk calls for is done, with that depth stated on the pull request: squash, branch deleted.
- Workflows use standard GitHub-hosted runners only. Never hold back a push or a check to ration runners.
- No personal details of any machine or person: no absolute paths, hostnames, account names or credentials.
- Removed means gone: no shims, aliases or compatibility paths.
- Swift 6 language mode, except the generated glue; Swift Testing, not XCTest.

## Code Review Rules

Report only a real problem: one that breaks the issue's acceptance criteria, a rule written in this file (quote it) or correctness, and say how it fails: the input, state or step, and what goes wrong. If you cannot say how it fails, it is not a finding. Leave formatting, lint and anything CI catches to CI, and skip any convention that is not written down. Check the whole tree, not only the diff, and name each finding by the check it breaks.

- **Done.** The acceptance criteria are met, the change was run for real in the conditions it will meet and not only compiled, new behavior has a test that was seen failing first, and what the pull request claims is true. A test that asserts absence has a witness: the same path with the condition removed produces the thing.
- **True.** A comment, doc, instruction file or contract statement the change touches or leaves untrue is a finding, fixed in the same change. New prose follows the standard under Writing for its kind. A claim of completeness ("all callers updated") is checked by searching, not accepted.
- **Nothing left behind.** Dead code, shims, old names and references to removed things.
- **Every path.** A permission, check or interpretation of a value holds at every door, including one the change adds, and in every copy of the logic: the server and the working copy, a fallback, a retry. Nothing is exempted by a name or field someone else controls.
- **Check and write are one step.** A decision is made on the state the write commits, with no wait, retry or asynchronous boundary between. Intent kept for a retry is captured, unchangeable, when it is sent, and announcements follow the order the writes were admitted.
- **Report only what is known.** Success, absence, completeness and current authority are claimed only on evidence that proves them: a refusal does not prove a write never committed, an old receipt does not prove present access, a partial snapshot is not a full inventory. A failure is not cleared by an unrelated operation.
- **Keep what people made.** A refused, failed or uncertain write is kept where the person can get it back, never dropped or rolled over newer work. Clean-up acts only on what it proved gone, and an edit keeps every byte it did not mean to change.
- **Real conditions.** Real clocks and dates, number ranges across languages and SQLite, runtime limits, slow or absent peers, untidy input, other platforms and file systems. One bad item, slow peer or hiccup stays contained and never takes down the batch, the folder or the job.
- **Flaky tests.** An unexplained flaky test is a finding: reproduce it, or say exactly why it cannot recur.

Mark a finding blocking when it changes how Marfa behaves or breaks a criterion or rule, and a quick fix when it is a name, a stale reference or a wrong count. Keep a problem that was there before the change apart from findings against it, and list it only if it is clearly wrong and would keep coming up.
