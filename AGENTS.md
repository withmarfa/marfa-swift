# marfa-swift

This repository is the Swift package `Marfa`, product `Marfa`: a thin layer over `MarfaCore`, the Rust engine every native client embeds, built from the monorepo `withmarfa/marfa`. The package does no networking, storage or syncing of its own; the core does all three.

## Layout and build

- Five targets. `MarfaCoreFFI` is the core as a binary, `Frameworks/MarfaCoreFFI.xcframework`, gitignored. `MarfaCore` is the Swift glue UniFFI generates for it, committed and never edited. `MarfaCoreNames` gives the glue's records names a module with records of its own can reach. `Marfa` is the hand-written layer apps import. `MarfaTypes` is the server's wire shapes, generated by swift-openapi-generator from the pinned commit's `openapi.json`, committed and never edited, and a product of its own.
- `core.pin` names the monorepo commit the package is built against, always one on its `main`. `scripts/core.sh` checks that commit out (the monorepo is private, so the clone needs access to it), runs its `core/bindings/swift/build.sh`, which installs the cargo-swift version it names, and copies the framework and the glue in. It then builds the generator `generator/Package.swift` pins and writes `Sources/MarfaTypes` from the same commit's `openapi.json` under `generator/openapi-generator-config.yaml`. CI fails when the committed glue or wire types differ from what the pinned commit generates.
- After `scripts/core.sh`: `swift build` to build, `swift test` to test. The live tests run against the server `MARFA_API_URL` and `MARFA_API_KEY` name, and are skipped by name without them; `MARFA_LIVE_REQUIRED` turns a missing server into a failure. The monorepo's `core/scripts/server-up.sh` boots one from the same pinned commit, once `pnpm install --frozen-lockfile` and `pnpm --filter "@withmarfa/server..." build` have run in that checkout; it exports `MARFA_TEST_URL` and `MARFA_TEST_KEY`, to be exported as `MARFA_API_URL` and `MARFA_API_KEY`.
- `Examples/MarfaSample` is the sample app for macOS and the iOS simulator. Its project is generated by `xcodegen generate` and gitignored.
- `.github/workflows/ci.yml`'s `Build + test` does all of the above on the runner pool: the lint, the core at the pin, the check of both generated sources, a booted server with the live tests required, both sample builds, and the sample's scenario run offline and back.

## Versions

- **Every version is the previous one plus 0.0.1, whatever the size of the change.** The first version is 0.0.1.
- A commit's type (`feat`, `fix`, a breaking change) never decides a version.
- A version exists only as a git tag on the monorepo, and tags are the maintainer's. Nothing publishes this package yet, so nothing can depend on it by URL; this repository has no release workflow, and agents never add one, create a tag, or write a version into a file.

## In force

- American English in code, comments and commits. Scoped Conventional Commits (`feat(package):`, `fix(ci):`).
- Feature branches and pull requests; never push `main`. A session merges its own pull request once every required check is green and every finding its reviewers raised is fixed: squash, branch deleted.
- Every Actions workflow runs on the self-hosted runner pool, never on GitHub-hosted runners.
- No personal details of any machine or person in this repository: no absolute paths, hostnames, account names or credentials.
- Removed means gone: no shims, no aliases, no compatibility paths.
- A comment survives only if it explains a why the code cannot.
- Swift 6 language mode; Swift Testing, not XCTest.
